# カスタム文章からの単発作画

この改訂は隔離コピーで実装・検証した。母艦の稼働用checkout、実`config`、毎時timer、Picoプログラムには適用していない。外部画像生成APIへの切替や実画像生成の追加呼び出しも行っていない。

## 画面と入力

- メイン画面に現在選択中の情報取得プロンプトと作画テイストを表示する。`GET /v1/topics`と`GET /v1/styles`を画面表示時、フォーカス復帰時、および定期的に実`config`から読み直す。これは**次に開始する生成の現在設定**であり、過去作品の設定ではない。
- 「文章から直接作画」は自由入力を1回送信する。テンプレート一覧、自動ローテーション、打鍵ごとの保存はない。空白のみ、NUL文字、4000文字超を拒否する。
- `GET /v1/generate/custom-text`は最後に受理したカスタム文章1件を返す。画面を開き直すと入力欄へ戻す。ただし復元応答の前にユーザーが入力を始めた場合、その入力を上書きしない。
- 生成中の進捗と結果は従来の`GET /v1/generate/status`を使う。成功時は最新画像とカレンダーを読み直す。

## APIと保存

- 従来の`POST /v1/generate`本文`{}`はニュース調査を伴う手動生成として維持する。`{"custom_text":"..."}`だけを新しいカスタム経路として受け付ける。Host、Origin、同一originのFetch Metadata、専用ヘッダー、LAN送信元制限を両方に適用する。
- カスタム要求を受け付ける際、選択中の作画テイストと再試行設定をジョブ要求へ固定する。カスタム実行は題材選択を変更せず、毎時生成の設定・slotも消費しない。内部ジョブ識別子は設定可能な題材IDと衝突しない値を使う。手動ジョブは従来どおり負のslotと共通の排他ロックを使用する。
- `state/last_custom.json`に最後に受理した文章だけをatomic writeする。実行用の要求は`state/manual_requests/<run_id>.json`に一時保存し、ワーカーの終了時に削除する。開始後はジョブごとの文章を`state/custom/<slot>.json`へ保存する。これらはテンプレート一覧ではなく、実行と復旧の内部記録である。
- カスタム経路は情報取得call、ニュースJSON保存、URL検証、24時間URL重複判定を通らない。ダミーの出典URLやニュース要約は作らない。画像バックエンドには`custom_text`を明示した文章を渡す。画像生成の再試行、PNG検証、250×122の1bit正規化、履歴公開、latestの原子的切替、PicoへのPUSH登録とCodex画像試行ごとの実プロンプト証拠はニュース経路と共通である。
- 公開フレームのメタデータに`input_kind=custom`、`custom_text`、生成時のテイストID・名前・指示文と`source_urls=[]`を保存する。日別の画像履歴には入力文章を選択可能な欄で表示する。ニュース作品は出典URLと、保存されている場合は生成時の情報取得指示を表示する。古い作品に存在しないメタデータは補作しない。Picoが読む`/v1/latest`の形式は変更しない。

## 検証

- 隔離コピーの`python3 -m unittest discover -s tests -q`で新旧70件成功。カスタムの調査スキップ、出典URLなしの保存、画像段階のCodex実プロンプト証拠、開始時のテイスト固定、前回文章1件の復元、拒否した要求での保持、HTTPの同一origin制約、通常題材ID`custom`との非衝突を確認した。さらに、実HTTP POSTから別プロセスの模擬画像バックエンド、PNG/RAW履歴公開まで通した。
- 実Google Chromeのheadless画面から文章を入力してPOSTし、再読込後の復元を確認した。実`config`相当のテスト設定を変えた後、メインの現在設定だけ更新され、履歴には作品生成時のテイストが残ることを確認した。画像生成は模擬PNGを使い、外部画像ツールやPico本体を呼んでいない。
- 本番反映前に、稼働中サービスのバックアップと段階的切替を別途確認する。特に実Codexによるカスタム文章からの画像品質とPico実画面での表示は未検証である。
